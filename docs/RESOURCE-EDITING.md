# 通用资源的并发编辑

`/api/resources/<kind>` 的普通资源接口使用强 ETag，防止用旧表单覆盖别人刚保存的数据。GET 列表和单条、POST、PUT 的记录带 `_etag`；单条响应另外提供带引号的 HTTP `ETag`。它是服务器计算的不可解释标识，覆盖完整存储记录，包括客户端看不到的受管字段。

更新或删除前，应保留**打开记录时**的标识：

```http
PUT /api/resources/locations/RESOURCE_ID
If-Match: "REVIEWED_64_HEX_ETAG"
Content-Type: application/json

{"name":"Reviewed name","city":"Shanghai"}
```

PUT 仍使用完整的可编辑字段替换语义；引用、受管字段和业务约束依旧校验。DELETE 使用同一个 `If-Match` 机制。PUT 也允许在 JSON 中回传读取到的 `_etag`，服务器会将它剔除后再校验与保存；若同时传 header 和 body，两者必须一致。POST 不接受旧 `_etag`。标识不写入资源、不进入 `/api/export`，不能自行生成或跨资源使用。

| 响应 | 含义与处理 |
| --- | --- |
| `428` | 未提供审阅版本；先读取记录，再提交其具体 ETag |
| `412` | 记录已改变；保留草稿，重新读取并核对差异 |
| `400` | 标识格式或业务数据无效；不接受 `*`、弱 ETag 或多个候选标识 |
| `401` / `403` | 会话、令牌或权限已变化；不能借旧表单继续写入 |

服务器在写事务中同时比较版本并复核当前操作者权限与安全代次，两个使用同一版本的并发写入只会有一个成功。冲突响应不返回记录内容；客户端新 GET 会重新执行权限和租户检查。

浏览器遇到冲突会保留草稿，展示自己和服务器修改的字段。未重叠的变更可组成合并建议，重叠字段需要逐项选择；确认后只回填表单和已核对的基线，仍需再次保存。此后若又有并发修改，仍返回冲突。删除也需要核对新记录后再确认。密码字段在冲突时清空，草稿导出不包含密码、认证令牌或 `_etag`。

不要在保存失败后自动获取最新 ETag 并原样重试旧 payload，这会绕过用户审阅的目的。自动化若以外部期望状态为准，也应显式读取当前状态、评估差异，再有条件地提交。

配置工具的 `/api/resources/provisioning-profiles` 保留其专用 `revision` / `expectedRevision` 协议；文档、配线、策略、凭据等专用操作继续使用各自的摘要或修订，不混用通用资源 ETag。原有 CSRF 和 API scope 检查保持有效。API 调用方需适配这个写入契约，旧的无条件 PUT/DELETE 不再成功。
