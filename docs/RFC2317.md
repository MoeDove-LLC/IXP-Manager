# RFC 2317 offline review bundles

The RFC 2317 generator produces a complete child zone and a parent delegation
fragment for review. The parent aliases point to PTR owners in the child, with
NS records at the child name. The offline merge workflow combines the reviewed
records with an exact local parent snapshot to produce a complete parent
candidate alongside the complete child. [RFC 2317](https://www.rfc-editor.org/rfc/rfc2317.html)

The provisioning console has a separate paired review and approval workflow
for complete RFC 2317 bundles. Ordinary `dns-arpa` profiles still require a
complete authority zone. Use the merged pair and its own approved download
when checking the current parent and child on the target.

## Prepare, inspect and check

Review the synthetic shape in
[`tools/provision/example-rfc2317.json`](../tools/provision/example-rfc2317.json).
Its parent checksum refers to the adjacent **synthetic** parent example, not a
production zone. For real work, obtain the correct parent owner's reviewed
snapshot and explicitly supply its identity, observed serial and per-owner facts.

```sh
ixp-provision rfc2317-render --input rfc2317-input.json --output review.json

ixp-provision rfc2317-check --file review.json --checksum REVIEWED_SHA256 \
  --parent-zone 2.0.192.in-addr.arpa. \
  --child-zone 128-131.2.0.192.in-addr.arpa. \
  --named-checkzone /usr/bin/named-checkzone

ixp-provision rfc2317-extract --file review.json --checksum REVIEWED_SHA256 \
  --parent-zone 2.0.192.in-addr.arpa. \
  --child-zone 128-131.2.0.192.in-addr.arpa. --output new-review-directory
```

Rendering writes a new 0600 canonical JSON bundle. Checking binds its exact
SHA-256 and expected parent/child identities. Extraction requires a new directory
and writes `child.zone`, `parent.fragment` and `review.json` as private files.
Existing files/directories are never replaced. Extraction is not installation;
an I/O failure can leave a partial private directory for inspection.

## Explicit contract

- Version 1 supports one canonical unicast IPv4 `/25` through `/32` prefix
  contained in one `/24`. The explicit `first`/`last` octets must exactly equal
  that prefix's range. The merge workflow requires the complete `/24` parent snapshot.
- The child is supplied explicitly and must be `first-last.PARENT`. This limited
  naming convention prevents reusing one child identity for different ranges.
  Slash labels, arbitrary alternate names, out-of-tree children, non-CIDR ranges
  and repeated CNAME delegation chains are not supported by this milestone.
- Each parent address owner in the range must appear exactly once. A claim is
  either `state:"absent"` with no target, or `state:"cname"` with exactly the
  generated child target. An existing PTR, unknown state, duplicate owner,
  out-of-range owner or different target is rejected.
- The delegation owner must equal the child. It must be explicitly absent or
  have `state:"ns"` and exactly the proposed NS set. The explicit parent TTL is
  bounded; changing an existing delegation target is not silently authorized.
- NS targets and SOA names use the existing strict hostname/RNAME checks and
  must be outside the parent/child reverse namespace. In-zone glue is not
  invented. PTRs require explicit unique addresses inside the block and explicit
  hostnames. No suffix-derived names or implicit active-only filtering is used.
- The child SOA serial is a frozen, nonzero caller value. An explicitly new child
  cannot also declare an old serial. An existing child requires
  `previousChildSerial`; the new value must advance it under the existing RFC
  1982 comparison, including valid wrap and rejection of the ambiguous half-space.
  This checks the declared baseline only, not a live server or persisted ledger.
- The parent snapshot checksum and observed SOA serial are references supplied
  by the operator. The generator does **not** read or authenticate that complete
  snapshot. Owner claims are checked for internal consistency and exact scope;
  they are not proof that the parent still contains those records.

The bundle records `approved:false`, `activated:false`,
`parentIntegrated:false`, and `parentSnapshotVerified:false`. Validation requires
exact regeneration of both contents, metadata and file hashes from the normalized
input. Changed scope, serial, record data, file paths or authority flags are
rejected. JSON rejects duplicate/case-alias fields, unknown fields, trailing
documents and excessive sizes/structure.

## What native checking proves

`named-checkzone` parses the complete child and a **synthetic parent wrapper**
containing the fragment. The wrapper is temporary and is not an output artifact.
The parent result is labeled `native-synthetic-wrapper`, never complete parent
authority or integration. The fragment has no SOA or global `$ORIGIN`/`$TTL`
directives; every emitted NS/CNAME owner and target is explicit. Native parsing
does not prove parent ownership, conflict-free integration, parent serial
advancement, forward resolution, secondary service or deployment.

## Merge a complete local parent snapshot

Supply the parent snapshot from the review and choose its next SOA serial
independently of the child. The commands below use the synthetic `/30` example,
whose reviewed parent SOA serial is `41`. Use each reviewed bundle's SHA-256
when checking or extracting it. [RFC 1982](https://www.rfc-editor.org/rfc/rfc1982.html)

```sh
ixp-provision rfc2317-merge --file review.json --checksum REVIEWED_SHA256 \
  --parent-zone 2.0.192.in-addr.arpa. \
  --child-zone 128-131.2.0.192.in-addr.arpa. \
  --parent-snapshot tools/provision/example-rfc2317-parent.zone \
  --parent-serial 42 --named-checkzone /usr/bin/named-checkzone \
  --output merge.json

ixp-provision rfc2317-merge-check --file merge.json --checksum MERGED_SHA256 \
  --parent-zone 2.0.192.in-addr.arpa. \
  --child-zone 128-131.2.0.192.in-addr.arpa. \
  --named-checkzone /usr/bin/named-checkzone

ixp-provision rfc2317-merge-extract --file merge.json --checksum MERGED_SHA256 \
  --parent-zone 2.0.192.in-addr.arpa. \
  --child-zone 128-131.2.0.192.in-addr.arpa. \
  --named-checkzone /usr/bin/named-checkzone --output checked-zones
```

- The parent snapshot must match the reviewed bytes, apex SOA serial, parent
  identity and per-owner claims. An existing PTR or unrelated CNAME at a claimed
  address, a different delegation NS set, an overlapping classless delegation,
  or records below a claimed owner are rejected. Already matching records keep
  their original TTLs and bytes.
- The merge changes the parent SOA serial token and appends exactly the missing
  reviewed NS and CNAME records. Other parent bytes and the complete child bytes
  are preserved. The supported master-file subset is an unsigned, self-contained
  UTF-8 file of up to 1 MiB, with IN-class SOA, NS, PTR, CNAME, A, AAAA, MX and
  quoted TXT records. `$INCLUDE`, `$GENERATE`, additional `$ORIGIN` directives,
  wildcards, DNAME and DNSSEC data are rejected before BIND runs.
- Each command verifies the complete source parent and candidate with
  `named-checkzone` using local integrity checks and full canonical dumps. A
  native RRset comparison verifies the exact additions and parent SOA advance.
  The complete child must also pass the native checker. [BIND `named-checkzone` documentation](https://bind9.readthedocs.io/en/stable/manpages.html#named-checkzone-zone-file-validation-tool)
- The merge bundle contains the original parent snapshot and both candidate
  files. Extraction writes `parent.zone`, `child.zone`, and `merge.json` into a
  new private directory. Keep the bundle and extracted files private alongside
  the original operator review. All output is for offline review.

Local snapshot verification and native RRset checks set the corresponding
receipt fields. The file's `approved`, `activated`, and `liveParentVerified`
flags describe the offline generator. Keep the canonical bytes for import.

## Approve the two zones together

From Configuration Center, choose **导入 RFC 2317 合并包** and select the
canonical `merge.json`. A staff browser session can import and check the
bundle. The draft stores the source snapshot and both candidate files in an
encrypted artifact. Its preview shows the complete child and reviewed parent
delegation and alias changes. Review the previous and next SOA serials for
both zones, then run validation. The configured `named-checkzone` checks the
source parent, the complete parent candidate and the complete child.

A browser administrator can approve the exact validated revision. The two
zones share the normal RFC 1982 ledger with other reverse-zone revisions, and
each maintains its own serial. A change to either approved head invalidates a
pending pair. When the submitted parent snapshot has the same serial as a
retained approved parent, its SHA-256 must also match that artifact. An
ordinary DNS revision cannot replace a parent with an active RFC 2317
delegation through inventory-only rendering.

Download the approved pair while both zones still point to that revision. The
download contains the exact imported bytes and returns the file SHA-256 in
`X-Config-SHA256`. Manager approval appears in the revision metadata and audit
records. Confirm the actual target files and service state before deployment.

## Verify the approved pair against the target files

Use the exact current approved download and its `X-Config-SHA256` response
header. Supply the expected zones and the absolute paths to their current
static master files. For a new child, supply its intended leaf under an
existing directory so the command can verify that leaf's absence.

```sh
ixp-provision rfc2317-preflight --file rfc2317-complete-zones.json \
  --checksum APPROVED_DOWNLOAD_SHA256 \
  --parent-zone 2.0.192.in-addr.arpa. \
  --child-zone 128-131.2.0.192.in-addr.arpa. \
  --parent-file /srv/dns/2.0.192.zone \
  --child-file /srv/dns/128-131.2.0.192.zone \
  --named-checkzone /usr/bin/named-checkzone
```

The target parent must match the bundled parent snapshot byte for byte under
its reviewed SHA-256. The existing child must have the approved previous apex
SOA serial and zone identity, including when that serial is zero. Both target
files use the same bounded complete master-file subset as the merge. Symlinks,
special files, missing intermediate directories, and active `$INCLUDE` or
`$GENERATE` directives are refused before BIND reads input. A `.jnl` sidecar
also prevents treating one static file as the complete current zone. [BIND journal behavior](https://bind9.readthedocs.io/en/stable/manpages.html#named-journalprint-scan-the-contents-of-a-zone-journal-file)

Native BIND checks the parent snapshot and candidate, the child candidate, and
the existing child when present. The command compares file identity, digest
and presence again after those checks. Its JSON result contains the bundle
digest and each zone's current and candidate digests and serials. For an
absent child, `current` contains only `present:false`.

`targetFilesVerified` covers these local path observations. The command reads
no service configuration, contacts no DNS server, and leaves `activated:false`.
An installation must recheck the same evidence at the moment it changes either
file.

## Install on a bound local BIND authority

The installer requires both zones to be configured on the same local BIND
authority as static, unsigned primary zones. Use absolute master-file paths and
numeric loopback endpoints for authenticated `rndc` and authoritative TCP DNS.
For an initially unloaded new child, predeclare the child with its intended
master-file path, explicit `allow-update { none; };`, `dnssec-policy none;` and
`inline-signing no;`. Enable `allow-new-zones yes;` for that view so the
authenticated `showzone` command can prove the configuration before the first
load. These options are configured by the operator. [BIND control commands](https://bind9.readthedocs.io/en/stable/manpages.html)

```sh
ixp-provision rfc2317-install --file rfc2317-complete-zones.json \
  --checksum APPROVED_DOWNLOAD_SHA256 \
  --parent-zone 2.0.192.in-addr.arpa. \
  --child-zone 128-131.2.0.192.in-addr.arpa. \
  --parent-file /srv/dns/2.0.192.zone \
  --child-file /srv/dns/128-131.2.0.192.zone \
  --named-checkzone /usr/bin/named-checkzone \
  --rndc /usr/sbin/rndc --rndc-key /srv/dns/private/rndc.key \
  --control-endpoint 127.0.0.1:953 --dns-endpoint 127.0.0.1:53 \
  --exclusive-maintenance
```

Run in an exclusive maintenance window that excludes external zone-file and
BIND configuration writers. The command locks both containing directory inodes
for cooperating installers. Run as the effective owner of both directories and
existing master files. Existing file mode and group are retained. Ensure that
the authority can read a new child's `0600` master file. The Linux target needs a
filesystem with `O_TMPFILE` support and a mounted `/proc` for file staging.

The installer verifies the approved checksum, offline native checks, the exact
current files and BIND serials before writing. It persists a private journal
alongside the parent master file. The child file is installed and reloaded
first. Only authoritative TCP SOA and authenticated BIND readback of that child
allow the parent to be changed. The returned `activated:true` receipt requires
both candidate master files and their corresponding loaded serials.

If the command is interrupted or reports an uncertain result, repeat it with
the same options and `--resume`. The journal binds the approved pair and local
target. Resume compares both candidate and original file digests with BIND
readback before taking the next step. Keep the journal and the approved bundle
until the installation is complete. A partially published pair continues
forward to the approved serials. A corrective release should use new serials
instead of restoring a stale SOA. [RFC 1982](https://www.rfc-editor.org/rfc/rfc1982.html)
